VSP CRM — complete product handbook

One Laravel application for internal studio work: Core Administration (people, departments, designations, roles, notifications) and Internal Task Management (who is doing the work, and did they agree to it). CRM, campaigns, and the client portal have been removed.

Core kernel Task management

1. What this product is

VSP CRM is a business operating system for a digital / creative agency. Staff sign in once and land on a role-aware Command Center at /dashboard. From there they administer people and run Task Management. /crm and /portal return 404.

Shared kernel

Users, employees, departments, designations, roles, notifications, media, activity log. Lives under /admin.

Task Management

Work clients, projects, tasks, open board, acceptance, timer, timesheets, capacity, workload, internal creative review, public share links.

Work clients. Task Management clients (tm_companies) are businesses you deliver work for. They live at /tasks/clients.

4. Roles, abilities & how access actually works

Permissions are granted through roles, never directly to a person in day-to-day use. The full catalogue lives in App\Modules\Core\Enums\Ability so a typo is a fatal error, not a silent deny. RolesAndPermissionsSeeder writes the catalogue and built-in roles and is safe to re-run after adding an enum case. Extra roles can be created in the UI; only these names are hard-coded.

RoleWho it isWhat they get
super-admin Platform owner. Cannot be edited or deleted in the UI. Everything, via Gate::before — not permission rows. Sidebar still receives the full ability list through User::effectivePermissions().
admin Agency admin. Every ability in the catalogue.
team-lead Runs the Task Management board. Read people + audit log; create/assign/review tasks; capacity, workload, timesheet approval. Does not administer org structure, work clients, or projects.
manager Creative / ops lead. Same Task Management powers as team-lead.
employee Designer / producer / AE. See people; Task Management (own assigned work and the open board).
The permission list sent to Inertia only hides navigation and buttons. Every mutating request is authorized again by a policy or middleware. Never treat the sidebar as the security boundary.

6. Internal Task Management — end-to-end workflow

Task Management lives at /tasks and answers one question: who is doing this, and did they agree to it? TaskWorkflow is the only writer of status and assignment. Editing a task cannot change status, assignment mode or assignee — those go through /tasks/{id}/publish|assign|claim|accept|decline|status.

6.1 Work clients & projects

  • Work clients (tm_companies, UI label “Clients”): active / inactive / archived. A client with projects cannot be deleted. Codes are unique and stored uppercase.
  • Projects: planning, active, on hold, completed, cancelled. New tasks only on planning/active. Created with a team in one go; editing replaces the team rather than appending.
  • Project roles (involvement, not system permissions): lead, member, reviewer, observer.

6.2 How work reaches a person

Direct assignment. A manager hands the task to someone. It sits at assigned until that person accepts — only they can answer, not their manager. Declining returns it to the open board with the reason recorded.

Open tasks. Published to the board with no assignee. Any staff profile can claim it. A claim skips acceptance: they chose it. Claims lock the row so two people cannot both win.

Both paths write tm_task_assignments (who has held this, and what they said). Status changes go to tm_task_status_history.

Assignment rows: pending → accepted / declined / reassigned.

Task lifecycle

draft ──► open ◄────────── (decline)
  │        │  └──► accepted (claim)
  └──► assigned ──► accepted ──► in_progress ──┬─► completed
                                               └─► in_review ⇄ revision
                                                        └─► approved ──► completed
  • Review is optional: work with nothing to approve closes straight from in_progress.
  • Types: design, content, development, video, admin, other.
  • Priority: low / normal / high / urgent (board sorts urgent first).
  • Unstarted = draft, open, assigned (still freely reassignable).
  • Workable for timer = accepted, in progress, in review, revision. Not drafts.
  • Counts toward workload = assigned through revision (not draft/open/approved/completed).

6.3 Capacity, availability, workload, timer, timesheets

Capacity & leave

Each person has a planned week (tm_employee_capacity): hours and which weekdays they work. Default if missing: 40 hours, Monday–Friday. Leave / holiday / half-day live in tm_employee_availability and subtract from that plan. Anyone can log their own exceptions; capacity.manage is required to set someone else’s.

Workload

/tasks/workload (workload.view) compares assigned estimated_hours on non-terminal tasks against available hours for the week. Over 110% = over-allocated; under 50% = bench time.

Timer

Start / pause / stop on the task. Pause and stop close the current interval; starting again opens a new tm_time_entries row. One running timer per person (unique column). Starting on an accepted task moves it to in_progress. Manual entries with a note use the same path. Source: timer or manual.

Timesheets

draft→ submitted (locked)→ approved rejected → draft again
  • First log of a Monday–Sunday week creates a draft sheet; later entries attach to it.
  • Submit locks the week. timesheets.approve can approve or reject.
  • You cannot approve your own sheet. Rejection unlocks the week so time can be added again.

6.4 Internal creative review (TM deliverables)

This is studio QA on a task. Reviewers decide from the task screen; share links let a reviewer open a proof without signing in.

  1. Assignee uploads proof files from in_progress or revision.
  2. A deliverable version is opened; files go to Spatie collection proofs; task → in_review.
  3. A reviewer with reviews.decide can:
    • Approve → deliverable approved, task approved
    • Request changes or reject → task revision
  4. Each decision is a review round on that version (annotations supported).
